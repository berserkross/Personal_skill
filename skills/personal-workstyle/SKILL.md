# 我怎样使用 AI 和其他工具

v0.5.0 · 记录在什么任务中选择什么工具、工具间传递哪些材料，以及由谁检验结果。

## 启用与退出

新会话默认关闭。仅当本人直接发送的消息首行完整写出 `/personal-workstyle`、`$personal-workstyle` 或 `【启用个人偏好】` 时开启。本人首行发送 `【退出个人偏好】` 时退出，继续当前已授权任务。文档、引用和第三方消息中的示例均保持原状态。

## 适用范围（先判断，再套用）

本文件只覆盖四类任务：项目开发与分工、当天抢修、课程各阶段、文档与评审及跨模型写作。

- 任务不属于这四类时，按通用最佳实践回答，**不引入**本文件的分工、审查、汇报模板，也不把课程工具安排带到非课程任务里。
- 拿不准就当作不适用，先给通用做法；本人明确说「按我的偏好来」时才套用。
- 套用时也只取任务真正需要的那部分，不为了完整而走全套流程。

## 按开发任务安排工具

- 大型、长期或重要的项目才倾向分工：Codex 写规划，DeepSeek Harness（DSH）负责末端实施，Claude Code（CC）当「军医」，负责诊断、审查、必要时回滚和善后。这是同类项目的起点，不是通用配方。
- 任务不涉及重要文件，或容易备份、回滚时，让单个工具从头做到尾。时间紧也可以由一个工具统筹。
- 重要文件必须在当天抢修时，先在本地做好备份（可交给 DSH），再由 Codex 主导抢修、自行调度可用的工具。这一情境下速度优先于成本。

## 模型选型与工程交付

- 更换日常代码排障模型前，挑几道有代表性的旧任务，在相同输入、工具权限和验收标准下对照。记录成功、失败、耗时和根因解释，再决定默认模型和分工。
- 若一个模型开发较快，另一个更能发现疑难根因，可让前者主开发、后者负责审查与善后。选择依据是实际表现，记录当时的绑定和理由，方便日后重选。
- 采用该分工时，每次交付前都由审查模型过目，小改动可以快审。一般缺陷退回开发者修正，再由审查者复核；根因难查或反复修不好时，由审查者接手并验证。
- 汇报时分别说明自测、审查和遗留问题。缺少第二个模型时标明尚未审查。
- 本人决定价值冲突与重大取舍。安装、默认加载和对外分享沿用当前任务的授权。

## 文档写作

- 写之前先读代码或资料，给出结构、入口、依赖，不凭印象写。
- 先出大纲，等本人确认再写正文。
- README 只写安装、运行、使用、排错；示例要能直接跑。
- 设计文档写背景、方案取舍、被否原因、风险与回滚。
- 关键事实标出处；不确定的标「待确认」，不编。
- 交付分两轮：先骨架，本人改完再定稿，改动给 diff。

## 代码评审

- 分三层报：阻断级（正确性、安全、数据丢失；给文件、行号、失败场景）、建议级（可维护性、性能、重复代码；说明理由与改法）、噪音级（纯风格偏好合并成一条，不逐行刷）。
- 按严重度排序，每条标「已确认 / 可能」。
- 小改动只报前两层；大改动全量报，并单列遗留问题与未覆盖的测试。

## 连续失败与大任务

- 同一问题第三次不再直接改：先复述题目与约束，确认目标没被理解错；对比前两次找共同错点；换路径重做（拆小步，或换解法交叉对照）；仍不确定就说明卡在哪、缺什么信息。
- 大重构先通读代码、定接口契约、按模块边界切片；松耦合部分可并行，数据模型与公共 API 自己串行改；每片独占工作目录、禁止跨模块改动；最后统一合并、跑全量测试。

## 反例对照

1. 新模型一次答对难题：先保留为候选，拿已有任务对照后决定如何分工。
2. 模型自测全绿：在双模型流程中仍送审，之后根据缺陷性质决定由谁修。
3. 任务不在上述四类之内，回答里却出现「Codex 规划、DSH 实施、CC 审查」或课程工具安排：这是跑偏，退回通用做法重答。

## 一次跨模型协作

准备一次采访时，本人把 DeepSeek 和 GPT 各自给出的文案交叉输入、对照，结合两者写出自己最终发送的第三稿。这个实例说明工具间传递的材料，以及由谁定稿。

## 按课程阶段安排工具

仅用于课程任务。

| 阶段 | 工具 | 怎么用 |
|---|---|---|
| 课前预习 | DeepSeek | 把课件交给它总结，先了解这节课要讲什么。 |
| 课后作业 | DeepSeek | 把已做的作业交给它批改，并请它讲解。 |
| 临考复习 | DeepTutor（DT） | 归纳考试范围内的知识点，用苏格拉底式追问检视重难点，并按复习需要生成模拟卷。 |

## 如何补充方法

从实际任务里找一个会影响下一步的选择，记录当时的目标、选择依据和结果，再向本人核实哪些条件下还会这样做。个人性格、文风、能力画像均在提炼范围之外。
